# Agent Trellis 初始化

构建能够准确描述目标仓库当前状态，并可在使用中生长的最小治理层。

## 不可突破的边界

严格分为两个阶段：

1. 执行只读审计并展示初始化方案。
2. 只有用户明确确认该方案后才写入。

用户提出“初始化”只会启动第一阶段，不等于对第二阶段的确认。确认前不得创建、修改、重命名或删除文件。

本 Skill 不得提交、推送、重写历史、访问生产服务、操作物理系统或执行其他会改变外部状态的动作。保留已有规则和未提交修改。

## 第一阶段：审计并提出方案

检查目标仓库前，完整阅读[发现契约](references/discovery.zh-CN.md)。确定 Git 边界，并检查已有指令、源码、配置、测试、文档、构建入口、组件关系和高影响操作。

将源码、已提交配置和观察到的非变更性命令输出作为证据。冲突和无法验证的声明保持未知。不得把名称或看似合理的惯例当作事实。

根据已经建立的项目文档判断目标文档语言；无法明确判断时询问用户。

展示：

- 仓库边界和需要保留的未提交修改；
- 有证据支持的当前状态摘要与未知项；
- 长期事实的单一 owner map；以及
- 每个需要创建、合并或保持不变的文件。

说明各个条件 owner 的证据依据，然后等待明确确认。

## 第二阶段：生成并验证

确认后，完整阅读[生成契约](references/generation-contract.zh-CN.md)。使用 `assets/` 下对应语言的模板树。将每个占位符替换为有证据支持的值，或替换为 owning 文档能够安全保留的明确未知项。

谨慎合并已有文件。不得整体替换已有 `AGENTS.md`、政策、文档 owner 或项目 Skill。冲突需要用户决策时，停止并展示冲突。

只创建核心生命周期和有证据支持的条件 owner。每项事实只设一个 owner，其他位置使用链接。

随后阅读并遵守[验证契约](references/validation.zh-CN.md)。分别报告创建、合并和保留的文件，以及实际运行的检查和仍未解决的未知项。

## 后续运行

对于已经初始化的仓库，重复只读审计并提出漂移修复建议。不得充当上游模板同步器，不得删除项目定制，也不得重复创建 owner、Note、Work Item 或 Skill。
