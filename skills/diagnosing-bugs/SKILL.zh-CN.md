# 缺陷诊断

一种处理棘手缺陷的方法。只有明确说明理由时才能跳过阶段。

探索代码库时，在形成理论前阅读项目适用指导，以及相关的当前事实和决策 owner。

项目的安全与授权规则优先于自动化或收紧反馈循环的尝试。不允许无人参与复现时，使用项目允许的人工参与路径，并明确说明限制。

## 脱敏

本 Skill 会要求展示命令、输出和捕获的产物。**先隐去每一项秘密**，用 `<REDACTED>` 替代。围绕环境变量构建循环，使凭据留在环境中而非展示内容里。捕获的产物会携带认证头：只引用提供诊断信号的行。

脱敏后的输出不足以诊断时，说明情况并询问用户。

## 阶段 1：建立反馈循环

**这就是本 Skill 的核心。** 其余都是机械操作。如果针对该缺陷有一个**紧凑**的通过/失败信号（能因这个缺陷而失败），就能找到原因；二分、假设检验和插桩都只是在使用它。如果没有，再久地盯着代码也无济于事。

在这里投入更多精力。**积极尝试、发挥创造力、不要轻言放弃。**

### 构建方式，大致按以下顺序

1. 在能触达缺陷的测试边界上建立**失败测试**：单元、集成或端到端。
2. 针对运行中的开发服务器使用 **Curl / HTTP 脚本**。
3. 用 fixture 输入进行 **CLI 调用**，将 stdout 与已知正确的快照比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并断言 DOM、控制台或网络行为。
5. **回放捕获的轨迹。** 将真实网络请求、载荷或事件日志保存到磁盘，在隔离环境中沿对应代码路径回放。
6. **一次性测试程序。** 启动系统的最小子集（一个服务、模拟依赖），通过一次函数调用触发缺陷路径。
7. **属性测试 / 模糊测试循环。** 若缺陷表现为“有时输出错误”，运行 1000 个随机输入寻找失败模式。
8. **二分测试程序。** 若问题发生在两个已知状态之间（提交、数据集或版本），自动执行“启动状态 X、检查、重复”，以便使用 `git bisect run`。
9. **差分循环。** 将相同输入送入旧版与新版（或两套配置），比较输出。
10. **人工参与流程。** 最后手段。若必须由人操作，使用项目允许的人工参与路径。附带脚本适合该路径时，使用 `scripts/hitl-loop.template.sh` 保持循环有结构，并将捕获的输出反馈给你。

建立正确的反馈循环，缺陷就修好了九成。

### 收紧循环

将循环视作一个产品。拥有一个循环后，继续**收紧**它：

- 能否更快？（缓存初始化、跳过无关初始化、缩小测试范围。）
- 信号能否更明确？（断言具体症状，而非“没有崩溃”。）
- 能否更确定？（固定时间、随机种子、隔离文件系统、冻结网络。）

耗时 30 秒且不稳定的循环只比没有稍好；确定性强、耗时 2 秒的循环才足够紧凑，是调试利器。

### 非确定性缺陷

目标不是一次干净复现，而是**提高复现率**。将触发动作循环 100 次、并行执行、增加压力、缩小时序窗口、注入 sleep。复现率 50% 的偶发缺陷可以调试，1% 则不行，因此持续提高复现率直到可调试。

### 确实无法建立循环时

停止并明确说明，列出已尝试的方法。向用户请求：(a) 能复现的环境访问权限；(b) 已脱敏的捕获产物（HAR、日志、core dump、带时间戳的录屏）；或 (c) 添加临时生产插桩的许可。没有循环时，**不要**继续提出假设。

### 完成条件：能够打红的紧凑循环

当循环足够**紧凑**且**能够打红**时，阶段 1 完成：你能给出一个**已实际运行至少一次的命令**（脚本路径、测试调用或 curl），展示脱敏后的调用和输出，并满足：

- [ ] **能够打红**：触达实际缺陷路径并断言**用户的确切症状**，能在缺陷存在时失败、修复后通过。不是“运行不报错”，而是必须能捕获这个具体缺陷。
- [ ] **确定性**：每次结果一致；偶发缺陷则按上述方法固定在较高复现率。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **可在项目授权模式下运行**：允许时无人参与运行，否则使用项目允许的人工参与路径。

如果在该命令存在前，你已开始阅读代码以构建理论，**停下：直接跳到假设正是本 Skill 要防止的失败方式。** 没有能够打红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，观察缺陷出现并使结果打红。

确认：

- [ ] 循环复现的是**用户**描述的失败模式，而不是附近另一个失败。找错缺陷就会修错问题。
- [ ] 多次运行可复现失败；非确定性缺陷则达到足以调试的复现率。
- [ ] 已捕获确切症状（错误信息、错误输出或耗时），供后续阶段验证修复是否真正有效。

### 最小化

打红后，将复现缩减为**仍能打红的最小场景**。输入、调用者、配置、数据和步骤**每次只删一项**；每次删除后重跑循环，只保留对失败不可或缺的部分。

这样做的价值：最小复现缩小阶段 3 的假设空间，也会成为阶段 5 清晰的回归测试。

当**每个剩余元素都不可或缺**时完成：去掉其中任何一项都会使循环变绿。

在完成**复现和最小化**前，不要继续。

## 阶段 3：提出假设

在测试任何假设前，生成 **3–5 个按可能性排序的假设**。只生成一个假设会锚定于最先想到的合理解释。

每个假设都必须**可证伪**：写明它预测的结果。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让缺陷消失 / <改变 Z> 会让它更严重。”

无法写出预测的假设只是感觉：舍弃或澄清它。

**测试前向用户展示排序后的列表。** 用户常有能够立即调整排序的领域知识（“我们刚部署了与第 3 项有关的修改”），或知道哪些假设已排除。这是成本低、节省时间的检查点。不要阻塞等待；用户不在线时按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的一个具体预测。**每次只改变一个变量。**

工具优先级：

1. 环境支持时使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在区分假设的边界放置**定向日志**。
3. 不要“记录一切再 grep”。

**给每条调试日志加唯一前缀**，例如 `[DEBUG-a4f2]`。结束时一次 grep 即可清理。无标记的日志容易留下，有标记的日志容易移除。

**性能分支。** 对性能回退，日志通常不是正确工具。应先建立基线测量（计时程序、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

## 阶段 5：修复与回归测试

在修复前编写回归测试，但前提是存在**正确的测试边界**。

正确边界能让测试覆盖调用点实际出现的**真实缺陷模式**。若唯一可用边界过浅（缺陷需要多个调用者却只有单调用者测试，或单元测试无法重现触发问题的调用链），在那里编写回归测试会制造虚假信心。

**不存在正确边界本身就是发现。** 记录它。代码库架构阻碍了用测试锁定缺陷，应将此情况带到下一阶段。

存在正确边界时：

1. 将最小复现转化为该边界上的失败测试。
2. 观察测试失败。
3. 应用修复。
4. 观察测试通过。
5. 对原始、未最小化的场景重跑阶段 1 的反馈循环。

## 阶段 6：清理

宣布完成前必须满足：

- [ ] 原始场景不再复现缺陷（重跑阶段 1 循环）。
- [ ] 回归测试通过，或已记录缺少适当测试边界。
- [ ] 所有 `[DEBUG-...]` 插桩已移除（用 `grep` 查找前缀）。
- [ ] 一次性原型已删除，或移至明确标记的调试位置。
- [ ] 正在创建 commit / PR 时，在其说明中写明最终成立的假设；否则将其写入诊断报告。
