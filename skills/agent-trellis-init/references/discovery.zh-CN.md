# 发现契约

## 先确定范围，再建立事实

解析目标路径及其最近的 Git 根。识别嵌套仓库和 submodule，不假设父仓库状态能够代表它们。用只读命令记录当前分支、HEAD、远端和未提交路径。绝不泄露配置、历史或环境输出中的秘密。

## 证据清单

只检查形成方案所必需的内容：

- 已有 `AGENTS.md` 文件及指令优先级；
- 源码和包边界；
- 已提交的配置和 schema；
- 组件之间的公开与内部接口；
- 构建、测试、lint、格式化和发布入口；
- 文档和当前事实 owner；
- 决策记录和临时工作跟踪；以及
- 能够改变生产数据、外部服务、凭据、金融状态、消息、已部署系统或物理设备的操作。

优先进行有界搜索和 manifest 检查。当安全性明确时，可以观察不会产生变更的 help、list、parse 和 dry-run 命令。不要仅因为文档提到某条命令就安装依赖或运行它。

## 证据等级

- **已建立：** 由源码、已提交配置或观察到的输出直接支持。
- **已有文档声明：** 由现有 owner 声明，但未独立观察。
- **未知：** 缺失、冲突、含糊或无法安全验证。

不得静默消解冲突。指出每个来源，在 owner 或用户解决前将该声明保持为未知。

## 方案结构

生成简明方案，包括：

1. Git 与仓库边界；
2. 需要保留的已有文件和未提交文件；
3. 当前组件和开发入口；
4. 未知项和相互冲突的声明；
5. 拟议 owner map；
6. 需要创建或合并的核心文件；
7. 条件 owner 的证据和理由；以及
8. 选定的输出语言。

最后请求用户明确确认是否写入所列变更。范围发生变化时，必须更新方案并重新确认。
